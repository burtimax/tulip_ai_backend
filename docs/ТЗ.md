# ТЗ (компактная версия для ИИ-агентов)

## 1. Контекст проекта

- **Проект:** AI-помощник по выращиванию тюльпанов.
- **Платформа:** web, mobile-first.
- **Язык MVP:** русский.
- **Стек:** React (frontend), .NET/C# (backend), PostgreSQL, Docker, Nginx.
- **Внешние интеграции:** OpenRouter (LLM), Plant.id (анализ фото).

Цель MVP: дать пользователю быстрый прикладной ответ по выращиванию тюльпанов, включая диагностику по фото, без обязательной регистрации.

## 2. Границы MVP

### 2.1 Входит в MVP

- AI-чат (текст + фото).
- Анализ изображений через Plant.id и использование результата в ответе LLM.
- История пользовательских взаимодействий на backend.
- База знаний (минимум просмотр контента).
- Форма обращения в поддержку.
- Логирование критичных ошибок и статистики.

### 2.2 Не входит в MVP

- Полноценный кабинет пользователя и сложные роли.
- Реалтайм-чат с оператором.
- Платежи/биллинг.
- Нативные мобильные приложения.

## 3. Ключевые бизнес-правила

- Сервис доступен без регистрации.
- AI-ответы носят рекомендательный характер, не медицинское/агрономическое заключение.
- При недостатке данных AI запрашивает уточнения или рекомендует обратиться в поддержку.
- Ошибки внешних сервисов не должны падать в «технический» UX: пользователь получает понятное сообщение.

## 4. Функциональные требования (для реализации)

### FR-CHAT

- Пользователь может отправить текстовый запрос.
- Пользователь может прикрепить изображения (`jpg`, `jpeg`, `png`, `webp`).
- Backend формирует ответ с учетом:
  - текста пользователя;
  - результата Plant.id (если был фото-анализ);
  - системного промпта по домену тюльпанов.
- Ответ должен быть прикладным и простым.

### FR-HISTORY

- Взаимодействия пользователя сохраняются и доступны для повторного просмотра.
- Пользователь может продолжить диалог/сессию в рамках доступного контекста.

### FR-KB

- Есть раздел с материалами базы знаний.
- Минимум: список материалов и просмотр материала.

### FR-SUPPORT

- Пользователь может отправить обращение в поддержку.
- В обращении: описание проблемы, опционально изображение и контакт.

### FR-OBSERVABILITY

- Логируются:
  - критичные ошибки приложения;
  - статистические события;
  - попытки и результаты вызовов LLM.

## 5. Нефункциональные требования

- Mobile-first UX.
- Валидация входных данных и файлов на backend.
- Ключи внешних API хранятся только на backend.
- Использовать HTTPS в окружениях выше локальной разработки.
- Учитывать ограничения внешних API (таймауты, размеры payload, лимиты).

## 6. Интеграции

### OpenRouter

- Backend отправляет запросы к LLM.
- Должна быть возможность менять модель без изменений frontend.
- Записывать метрики/результаты вызовов (успех/ошибка, длительность, токены при наличии).

### Plant.id

- Backend принимает пользовательское изображение и отправляет его в Plant.id.
- Ответ Plant.id преобразуется во внутренний формат и передается в контекст LLM.
- При ошибке анализа показывается пользовательское сообщение с мягким fallback.

## 7. Сущности БД (АКТУАЛЬНО ПО `AppDbContext`)

Ниже перечислена **текущая фактическая модель**, присутствующая в коде (`Infrastructure/Db/App/AppDbContext.cs` и связанные entities).  
Все имена таблиц/полей/ключей в БД приводятся к `snake_case`. Для сущностей `BaseEntity` и `UserEntity` применяется soft-delete фильтр (`deleted_at is null`).

### 7.1 `UserEntity` (таблица `app.users`)

Назначение: пользователь приложения.

Поля:
- `id: Guid`
- `confirmed_policy_and_documents: bool?`
- `created_at: DateTimeOffset`
- `created_by_id: Guid?`
- `updated_at: DateTimeOffset?`
- `updated_by_id: Guid?`
- `deleted_at: DateTimeOffset?`
- `deleted_by_id: Guid?`

Особенности:
- используется как связанная сущность для статистики и логов;
- фильтруется глобальным `HasQueryFilter(deleted_at is null)`.

### 7.2 `StatEventEntity` (таблица `stat.stat_events`)

Назначение: статистические события использования.

Поля (плюс поля `BaseEntity`):
- `user_id: Guid?` -> FK к `users.id` (удаление пользователя: `SetNull`)
- `session_id: long?`
- `type: string?`
- `data: string?`
- `duration_seconds: double?`

Базовые поля из `BaseEntity`:
- `id`, `created_at`, `created_by_id`, `updated_at`, `updated_by_id`, `deleted_at`, `deleted_by_id`.

### 7.3 `LlmUsageEntity` (таблица `stat.llm_usages`)

Назначение: журнал попыток запросов к LLM.

Поля (плюс поля `BaseEntity`):
- `input_json: string` (`jsonb`)
- `duration_ms: long`
- `is_success: bool`
- `llm_response: string?`
- `error_message: string?`
- `prompt_tokens: int?`
- `completion_tokens: int?`
- `llm_model: string?` (max 512)
- `cost: decimal?`
- `llm_request_id: string?` (max 128)

### 7.4 `LogEntity` (таблица по умолчанию EF, имя в snake_case)

Назначение: критичные логи приложения (в т.ч. frontend/backend).

Поля (плюс поля `BaseEntity`):
- `user_id: Guid?` -> FK к `users.id` (удаление пользователя: `SetNull`)
- `log_source: enum LogSource?` (`Backend`, `Frontend`)
- `log_type: string?`
- `log: string?` (`jsonb`)
- `log_message: string?`

Примечание:
- для `LogEntity` в текущем коде явно не задана схема в `SetSchemasToTables`; используется стандартное поведение EF Core + snake_case.

## 8. Ограничения для дальнейшего проектирования БД

Чтобы не расходиться с текущим кодом:

- Не добавлять в ТЗ «целевые» таблицы как уже реализованные, если их нет в `AppDbContext`.
- Любые новые сущности (чаты, статьи, обращения и т.д.) описывать как **планируемые**, с отдельной пометкой «не реализовано в текущем контексте».
- При изменении модели сначала обновлять `AppDbContext`/entity-классы, затем синхронно править ТЗ.

## 9. Критерии приемки MVP (сокращенно)

- Пользователь может задать вопрос и получить ответ AI.
- Пользователь может отправить фото и получить ответ с учетом Plant.id.
- Ошибки внешних сервисов обрабатываются без «падений» UI.
- Критичные события и вызовы LLM пишутся в БД.
- Основные пользовательские сценарии работают на мобильном экране.
