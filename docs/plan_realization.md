# План реализации чата (Tulip AI)

## 1) Цель

Реализовать чат с асинхронной обработкой пользовательских сообщений по теме выращивания тюльпанов, где сообщение может содержать:

- только текст (HTML-формат),
- только изображения,
- текст + изображения.

Ключевое требование: после отправки сообщения API сразу возвращает успешный ответ, а фактическая обработка выполняется в очереди. После завершения в чат добавляется ответ от нейросети.

---

## 2) Функциональные требования

1. Пользователь может:
   - создавать новый чат;
   - открывать старые чаты из истории;
   - отправлять сообщения в существующий чат.
2. Каждое сообщение имеет статус обработки.
3. Чат имеет агрегированный статус (например: есть ли сообщения в обработке).
4. При наличии изображений:
   - каждое изображение последовательно отправляется в PlantId (`create identification`);
   - из ответа берутся наиболее вероятные гипотезы по растению и болезням;
   - результаты по всем изображениям агрегируются.
5. Формируется prompt для `OpenRouterService`:
   - добавляется пользовательский текст (если есть);
   - добавляются агрегированные данные по растениям/болезням из PlantId.
6. Ответ LLM сохраняется как сообщение ассистента в этом же чате.
7. Исходное сообщение помечается обработанным, статус чата обновляется.

---

## 3) Нефункциональные требования

- Асинхронность: быстрый ответ API на отправку сообщения.
- Последовательность обработки в рамках одного сообщения (картинки по одной).
- Надежность: retry, таймауты, корректная фиксация ошибок.
- Наблюдаемость: логирование и метрики по этапам пайплайна.
- Безопасность: санитизация HTML, ограничения на размер/тип файлов.

---

## 4) Предлагаемая архитектура

### 4.1 Компоненты

- `Chat API` (синхронный слой):
  - CRUD чатов;
  - прием сообщений;
  - сохранение вложений;
  - постановка задач в очередь.
- `Queue`:
  - хранение задач на обработку сообщений.
- `Message Processor Worker`:
  - обработка сообщений из очереди;
  - вызов PlantId;
  - формирование prompt;
  - вызов OpenRouterService;
  - запись ответа ассистента и статусов.
- `Storage`:
  - хранение изображений (локально/S3-совместимо).
- `DB`:
  - чаты, сообщения, изображения, статусы, задачи.

### 4.2 Последовательность обработки сообщения

1. Пользователь отправляет сообщение в чат (текст, изображения или оба).
2. API:
   - валидирует вход;
   - сохраняет сообщение со статусом `Queued`;
   - сохраняет изображения;
   - создает задачу в очереди;
   - возвращает `200/202`.
3. Worker берет задачу и ставит сообщение в `Processing`.
4. Worker проверяет наличие изображений:
   - если есть: последовательно обрабатывает каждое изображение через PlantId;
   - если нет: этап PlantId пропускается.
5. По каждому изображению:
   - вызывается `create identification`;
   - выделяются наиболее вероятные значения:
     - тип/вид растения;
     - болезни/проблемы.
6. Формируется агрегированный контекст по всем изображениям.
7. Формируется prompt:
   - контекст PlantId;
   - пользовательский текст (если есть);
   - системные инструкции для ответа по теме тюльпанов.
8. Вызывается `OpenRouterService`.
9. Ответ LLM добавляется в чат как сообщение ассистента.
10. Исходное сообщение помечается как `Completed`, статус чата обновляется.
11. Клиент получает обновление (polling или realtime).

## 5) Модель данных (черновик)

### 5.1 Chat

- `Id`
- `UserId`
- `Title`
- `Status` (`Idle`, `Processing`, `Error`)
- `CreatedAt`, `UpdatedAt`
- `LastMessageAt`

### 5.2 Message

- `Id`
- `ChatId`
- `Sender` (`User`, `Assistant`, `System`)
- `HtmlText` (nullable)
- `Status` (`Queued`, `Processing`, `Completed`, `Failed`)
- `ErrorCode` (nullable)
- `ErrorText` (nullable)
- `CreatedAt`, `ProcessedAt` (nullable)

### 5.3 MessageImage

- `Id`
- `MessageId`
- `StorageUrl`
- `MimeType`
- `Status` (`Uploaded`, `PlantIdProcessing`, `PlantIdDone`, `Failed`)
- `PlantIdTopPlant` (nullable)
- `PlantIdTopDisease` (nullable)
- `PlantIdRaw` (nullable, json)

### 5.4 ProcessingJob

- `Id`
- `MessageId`
- `Status` (`Pending`, `Running`, `Done`, `Failed`, `RetryScheduled`)
- `Attempt`
- `NextRetryAt` (nullable)
- `CreatedAt`, `UpdatedAt`

---

## 6) API (черновой контракт)

- `POST /chats` — создать чат.
- `GET /chats` — история чатов пользователя.
- `GET /chats/{chatId}` — получить чат и сообщения.
- `POST /chats/{chatId}/messages` — отправить сообщение (htmlText + images[]).
- `GET /chats/{chatId}/messages` — список сообщений с пагинацией.
- (опционально) `GET /chats/{chatId}/events` — поток статусов (SSE/WebSocket).

### Ответ на отправку сообщения

- Возвращать:
  - `messageId`
  - `chatId`
  - `status=Queued`
  - `createdAt`

---

## 7) Правила обработки контента

1. Разрешить сообщение, если присутствует хотя бы одно:
   - непустой `htmlText`,
   - хотя бы одно изображение.
2. Санитизировать HTML по whitelist-тегам.
3. Проверять размер, тип, и количество изображений.
4. Для каждого сообщения фиксировать трассировку:
   - `chatId`, `messageId`, `jobId`.

---

## 8) Ошибки и устойчивость

- Таймауты на внешние вызовы (PlantId, OpenRouterService).
- Retry с backoff для временных ошибок.
- Ограничение числа попыток, затем `Failed`.
- При `Failed`:
  - сохранять диагностическую информацию;
  - переводить чат в `Error` только если это нужно по UX-логике;
  - показывать пользователю, что сообщение не обработано.
